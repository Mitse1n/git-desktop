# GitDesk 和 IntelliJ IDEA 内存与响应性能报告

> 本文保留优化前的调查记录。后续代码优化、同口径复测和最终结论见[优化前后报告](performance-optimization-2026-10-12.md)。早期探针未固定实际视图尺寸，其中的界面耗时不应与后续全尺寸测试直接混算。

测试日期：2026 年 10 月 12 日，Asia/Shanghai。本文保留当时的测试结论与数据，不代表后续修复后的版本已重新完成同样的性能测量。报告引用的原始数据和汇总随文归档，测试可执行文件及未引用的临时产物仅保留在本地。

GitDesk 在本次小型和中型仓库测试中，仓库打开、刷新及普通 Diff 的响应较快，基础进程负担也较小。但它有两个明确的性能边界：完整历史规模影响日志加载和主线程重建；大幅重写的文本 Diff 即使没有超出预览限制，也会产生秒级计算和很高的瞬时内存峰值。不能据此宣称它在所有 Git 操作上都比 IntelliJ IDEA 快。

本次完成了 GitDesk 的可重复自动基准和两个生产应用的现场内存采样。IDEA 可见界面的自动读取在本机发生超时，未取得可靠的同仓库、同操作可见响应计时，因此报告不提供虚构的 IDEA 毫秒数或速度倍率。IDEA 当前打开真实业务工程，GitDesk 现场窗口打开演示仓库，两个现有生产进程的占用只作为使用现场记录。

## 仓库打开和刷新

单位：毫秒，表内为中位数 / P95。

| 场景 | 核心快照 snapshot | AppKit 打开 ui_open | AppKit 刷新 ui_refresh |
| --- | ---: | ---: | ---: |
| small | 63.5 / 67.9 | 89.7 / 107.1 | 69.8 / 78.0 |
| medium | 150.5 / 167.9 | 202.4 / 259.5 | 163.5 / 212.0 |
| history100k | 808.6 / 1,019.5 | 1,079.7 / 1,140.9 | 835.4 / 888.9 |
| dirty | 147.6 / 190.1 | 213.8 / 294.3 | 155.7 / 164.2 |
| refs1000 | 211.7 / 223.5 | 323.9 / 416.2 | 226.3 / 259.4 |
| wide200 | 175.2 / 224.3 | 258.4 / 307.1 | 172.3 / 180.6 |
| 真实工程 | 146.2 / 156.9 | 229.3 / 264.4 | 152.7 / 191.3 |

small 到 medium 的打开耗时约从 90 ms 增至 202 ms，history100k 则约 1.08 秒。由于完整刷新读取所有提交的祖先关系，即使屏幕只显示默认的 2,000 条完整日志，也无法把总历史规模的成本限制在这 2,000 条内。

`ui_refresh` 测的是无外部变化时主动刷新。源码会比较新旧快照，未变化时跳过完整 UI 重建，因此它比“有新提交或分支变化后的刷新”更乐观。要测后者，应按复测手册在测试副本中插入固定变更后再刷新。

普通 snapshot 在默认过滤条件下约发起 10 次 Git 子进程调用；每次调用建立临时输出文件并等待完成。小仓库下，这些固定成本比图布局更显著。用不同语言或原生 UI 实现并不能消除系统 Git 的启动和查询成本。

## 搜索和主线程工作

单位：毫秒，中位数 / P95。

| 场景 | 核心文本搜索 | 含 250 ms 防抖的 AppKit 搜索 | 纯图布局 | 主线程完整 UI 重建 |
| --- | ---: | ---: | ---: | ---: |
| small | 15.2 / 15.8 | 277.1 / 281.7 | 0.18 / 0.18 | 3.7 / 4.1 |
| medium | 55.5 / 55.8 | 342.1 / 369.5 | 11.0 / 11.1 | 26.8 / 27.5 |
| history100k | 263.2 / 289.5 | 751.3 / 840.2 | 175.3 / 240.4 | 224.3 / 257.9 |
| dirty | 25.3 / 26.1 | 326.1 / 328.1 | 1.8 / 1.8 | 35.0 / 35.6 |
| refs1000 | 70.7 / 71.5 | 391.3 / 427.4 | 11.0 / 11.2 | 70.8 / 82.5 |
| wide200 | 61.6 / 64.3 | 369.7 / 391.6 | 48.4 / 48.9 | 68.3 / 70.9 |
| 真实工程 | 111.1 / 113.7 | 404.0 / 416.9 | 17.9 / 18.2 | 59.3 / 60.2 |

搜索的 250 ms 防抖是明确的交互取舍：降低逐字符查询频率，也让很小的仓库仍有接近四分之一秒的结果等待。表中的 AppKit 搜索交替执行 `needle` 和清空条件，包含两种状态；不能把它直接减去核心文本搜索来精确归因 UI 的额外成本。

最值得优先处理的是 history100k 的主线程工作：同步重建中位数 224 ms，P95 258 ms。相对于 60 Hz 的 16.7 ms 帧间隔，这段工作有明显干扰输入与动画的风险。refs1000 和 wide200 也有约 70 ms 的同步重建。它们是源码执行路径和离屏测量支持的结论，但尚未用可见录像测出具体掉帧数或滚动 FPS。

`updateUI()` 在主线程调用图布局，并构造全祖先字典、遍历当前分支祖先、计算列宽、重建分支和变更树。后台执行 Git 查询解决了 IO 阻塞问题，但没有把这些 CPU 工作全部移出主线程。

IDEA 提供 Git Log 索引，官方说明它改善日志筛选和历史查询。其首次建立索引和后续暖查询应分别测试；不能凭 GitDesk 没有语言索引就推断每次日志查询更快。[JetBrains Git Log 设置](https://www.jetbrains.com/help/idea/settings-version-control-log.html)

另一个功能差异是搜索范围。GitDesk 的文本/正则在当前加载的提交集合中筛选，默认 2,000 条，Load More 为 10,000。一个应用因范围更小而更快或未返回旧提交，不构成全历史搜索的性能胜利。

## 普通 Diff 和极端 Diff

各场景在独立进程中测量，单位为毫秒；内存峰值是该场景探针整个存活期的 RSS，包含预热，排除其他应用和子进程。

| 内容 | 计算中位数 | P95 | 进程峰值 RSS |
| --- | ---: | ---: | ---: |
| 双方各 1,000 行，修改 1 行 | 0.92 | 0.97 | 7.0 MiB |
| 双方各 5,000 行，修改 1 行 | 4.66 | 4.80 | 12.0 MiB |
| 双方各 5,000 行，忽略空白差异 | 18.09 | 19.25 | 15.6 MiB |
| 双方各 1,000 行，全替换 | 22.22 | 23.63 | 63.8 MiB |
| 双方各 5,000 行，全替换 | 519.18 | 536.82 | 713.9 MiB |
| 双方各 10,000 行，全替换 | 2,155.88 | 2,289.56 | 1,501.5 MiB |
| 超出字节预览上限 | 7.49 | 14.53 | 18.4 MiB |
| 超出行数预览上限 | 1.59 | 1.67 | 9.8 MiB |
| 含 NUL 的二进制输入 | 0.12 | 0.22 | 5.9 MiB |

1,000 行单行修改的实际控制器工作区预览约为 22 ms，包含文件读取、Git 调用、计算和视图应用，比纯算法的 0.92 ms 大。这说明普通小 Diff 的用户等待主要不在算法本身。

10,000 行全替换的双方文件合计 696,670 bytes，约 0.70 MB，低于 2,000,000 bytes；总行数恰好 20,000，也未超限，却出现约 2.16 秒计算及约 1.47 GiB 峰值 RSS。第一轮相同场景峰值约 1.71 GiB，说明峰值会随分配器、预热和系统状态波动，但高内存现象可以重复出现。不能用计算结束后几十 MiB 的 footprint 来否定过程峰值。

代码使用 Swift `difference(from:)` 比较标准化后的整行集合。Apple 文档给出的最坏时间复杂度为 O(n×m)；共同内容少的整文件重写因此是必要压力用例，而不仅是看文件大小。[Apple difference 文档](https://developer.apple.com/documentation/swift/array/difference%28from%3A%29)

另做了一轮每项 20 次的独立 Diff 测试，新增内核 physical footprint 峰值读数，得到以下结果；它们属于补充轮，不与上表混算：

| 内容 | 补充轮计算中位数 / P95 | 峰值 RSS | 峰值 physical footprint | 操作结束 footprint 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 双方各 1,000 行，全替换 | 22.2 / 23.1 ms | 56.0 MiB | 29.4 MiB | 21.4 MiB |
| 双方各 5,000 行，全替换 | 524.3 / 670.8 ms | 762.4 MiB | 435.8 MiB | 44.6 MiB |
| 双方各 10,000 行，全替换 | 2,059.7 / 2,126.9 ms | 1,646.2 MiB | 1,662.8 MiB | 34.7 MiB |

10,000 行全替换的 footprint 峰值约 1.62 GiB，进一步确认计算期间的实际内存负担。只有结束时采样会看到约 35 MiB，从而严重低估瞬时峰值。来源：[补充轮汇总](../output/performance/2026-10-12-diff-footprint/summary.csv)、[原始记录](../output/performance/2026-10-12-diff-footprint/raw.jsonl)。

Diff 计算在后台串行队列，能避免直接在主线程运行这个算法。请求 token 能阻止旧结果覆盖新文件，但已经开始的昂贵任务没有中途取消检查；快速连续切换大文件仍可能让最新请求排队。此排队风险由代码支持，本次没有取得它的可见界面尾延迟。

超限和二进制场景很快是因为拒绝文本比较，不是展示同等结果的算法优势。IDEA 官方高级配置的历史版本内容默认读取上限为 20,480 KB，GitDesk 的单文件读取和双方合计预览限制更小；必须在共同支持的范围内比较，或单独报告支持能力差异。[JetBrains 高级配置](https://www.jetbrains.com/help/idea/tuning-the-ide.html)

## GitDesk 探针内存

下表为同一场景完成一串打开、刷新、重建、搜索、详情及普通 Diff 后的最后读数；峰值 RSS 是该场景 UI 探针从启动到结束的累计峰值，不是某一次打开的新分配。

| 场景 | 最后 RSS | 最后 physical footprint | 进程峰值 RSS |
| --- | ---: | ---: | ---: |
| small | 90.0 MiB | 28.7 MiB | 90.0 MiB |
| medium | 103.3 MiB | 36.9 MiB | 107.4 MiB |
| history100k | 237.5 MiB | 68.5 MiB | 293.8 MiB |
| dirty | 133.3 MiB | 37.2 MiB | 135.5 MiB |
| refs1000 | 89.3 MiB | 40.9 MiB | 100.7 MiB |
| wide200 | 94.5 MiB | 38.7 MiB | 110.3 MiB |
| 真实工程 | 103.5 MiB | 45.3 MiB | 114.0 MiB |

离屏控制器空白基线的 RSS 约 36 MiB，footprint 约 11 MiB。它没有生产应用完整启动和可见窗口的所有成本，不能直接当作用户双击打开应用后的真实占用。RSS、footprint、虚拟地址空间和 Java heap 是不同指标，表中差异不应解释成测量矛盾。

每个 UI 场景经过重复查询后，Console 都到达 200,000 个 UTF-16 单元的上限。Console 有界保留是有效的内存保护，但这组短期记录没有证明长时间使用绝无泄漏。

## 生产应用的现场内存

在完整基准结束后，对两个原有应用进程继续采样 60 秒，每个应用取得 243 个读数；期间不再并行运行合成压力基准。采样结束时，分别保存主进程 `vmmap` 快照。

| 指标 | GitDesk 现场进程 | IDEA 现场进程 |
| --- | ---: | ---: |
| 主进程 RSS 中位数 | 68.4 MiB | 855.0 MiB |
| 主进程 RSS 采样最大值 | 84.3 MiB | 1,279.7 MiB |
| 进程树 RSS 中位数 | 68.4 MiB | 1,147.3 MiB |
| 进程树 RSS 采样最大值 | 84.3 MiB | 1,553.4 MiB |
| 结束时主进程 physical footprint | vmmap 显示 81.2M | vmmap 显示 2.4G |
| 主进程存活期 footprint 峰值 | vmmap 显示 148.2M | vmmap 显示 2.6G |

这不是公平的同场景胜负表。GitDesk 最近可读取窗口为 9 次提交的演示仓库，IDEA 日志显示打开约 6,662 次提交的业务工程，并运行浏览器辅助进程、Node 服务及插件辅助进程；启动时间和此前操作也不同。采样中 IDEA 还出现短时多核心活动，因此不能把它称为已确认完全空闲。RSS 树合计也会重复计入共享页。

它支持的实际结论是：**在这台机器当时的使用状态下，IDEA 的整个运行环境明显比 GitDesk 的演示仓库进程重。** 它不能支持“同一仓库省多少倍内存”，也不能说明已经启动的 IDEA 打开 Git 面板需要新增同样多的内存。后一问题必须测打开面板前后增量。

## 与 IDEA 的架构和使用情境对照

| 使用情境 | GitDesk 的成本来源 | IDEA 的成本来源 | 本次可支持的结论 |
| --- | --- | --- | --- |
| 只需要查看 Git | 原生 AppKit、Git 子进程、快照和图 | IDE 平台、JBR、插件、项目服务及 Git | GitDesk 基础工作范围更窄；现场占用较低，但不是同操作公平倍率 |
| IDEA 已经用于写代码 | 额外启动另一个应用和维护一份 Git 状态 | 已有 IDE 上新增 Git 窗口/缓存 | 应测新增占用，不能把整个 IDEA 成本归给 Git |
| 首次打开工程 | 查询 Git，不做语言项目分析 | 项目导入、扫描、语言分析及可能的 Git 索引 | GitDesk 避免语言分析成本；启动速度倍率待测 |
| 暖日志搜索 | 每次 Git log 及内存筛选，有加载范围限制 | 可复用 Git Log 索引 | IDEA 暖查询可能受益于索引；无本机直接计时 |
| 大量历史 | 全祖先读取和布局成本上升 | Git 日志缓存、索引及平台服务 | GitDesk 十万提交已测出约 1 秒打开和 224 ms 同步重建 |
| 大幅重写 Diff | 行集合差分的病态输入 | IDEA 的 Diff 实现和平台内存 | GitDesk 已测出高峰值；IDEA 同输入需按手册补测 |
| 多窗口和持续使用 | 每个控制器持有仓库快照、图和队列 | 多项目的独立数据与共享 IDE 平台 | 不能把单窗口占用直接线性乘以窗口数 |
| clone/fetch/push | 系统 Git、认证、网络和完成后刷新 | Git、认证、网络及 IDE 刷新 | 共同瓶颈不宜归因为 UI 技术；本轮未测 |

IDEA 的 `-Xmx2048m` 只是最大 Java 堆设置，不是当前占用，也不是整个进程的上限。JIT 代码缓存、类元数据、线程栈、native 分配及辅助进程都可能在堆之外。现场只读 `jcmd GC.heap_info` 曾显示已用堆约 770 MiB、committed 879 MiB、reserved 2,048 MiB；该快照与后文进程采样不是同一时刻，不能直接相减计算 native 内存。[JetBrains 内存解释](https://intellij-support.jetbrains.com/hc/en-us/articles/360018776919-IntelliJ-IDE-uses-more-memory-than-maximum-heap-size-Xmx)，[堆设置说明](https://www.jetbrains.com/help/idea/increasing-memory-heap.html)

## 自动发现文件变化和后台负担

GitDesk 的 watcher 是每 5 秒执行的 Timer，在仓库存在、非 busy/refresh、没有待处理搜索及模态窗口时刷新。它没有“应用不在前台就停止”的条件，因此现有代码下后台窗口也可能持续执行完整快照查询。

这意味着外部编辑器修改文件后，自动发现延迟与计时器相位有关，正常可能接近 0 到 5 秒，再加查询和队列等待；忙碌或模态状态可更久。这是代码路径推断，不是本次对外部修改的秒表实测。它和点击刷新耗时是不同指标。

完整刷新即使最终发现无变化，也先读取所有祖先。十万提交下定时轮询会重复付出较明显的查询成本。应另测后台 CPU 和耗电，不应从一次 0.8 秒 wall time 直接推算固定 CPU 百分比或续航损失。

## 优化顺序和复测目标

| 优先级 | 建议 | 原因 | 复测用例 |
| --- | --- | --- | --- |
| 高 | 为 Diff 增加工作量预算、可取消计算及降级路径；评估 Git/libgit2/专用算法 | 10,000 行全替换出现秒级等待和 GiB 级 RSS 峰值 | replace5000、replace10000，快速切换大文件 |
| 高 | 将图布局、祖先索引及其它可后台化的 UI 数据准备移出主线程 | history100k 主线程约 224 ms | ui_rebuild_main_thread，加可见录像 |
| 高 | 缓存全祖先结构，按 HEAD/refs 变化增量更新；把状态刷新和历史刷新分开 | 每次完整刷新重读全历史 | history100k 的 snapshot、ui_refresh 和后台 60 秒采样 |
| 中 | 降低大量分支时的树与菜单重建，缓存排列和筛选结果 | 千引用约 71 ms 主线程重建 | refs1000 |
| 中 | 调整日志搜索查询和防抖策略，并明确搜索范围 | 暖搜索仍有 250 ms 固定等待 | small/medium 搜索，历史最旧提交正确性 |
| 中 | 评估文件事件驱动或自适应轮询 | 发现延迟和后台重复工作 | 外部修改延迟、前后台 CPU |

这些是基于本次测量和源码的改进建议，本任务没有修改产品性能实现。优化后应首先保持结果正确、旧任务不回填，并使用同一套测试数据复核，再做同仓库 IDEA 对照。
